# 要件定義

## 1. システム概要

- 本MCPサーバは、AIエージェントがユーザーの注意を必要とするイベントやバックグラウンドタスクの進捗・完了を、ntfyを介してユーザーへ通知するためのインターフェースを提供する。
- ntfyの汎用MCPクライアントを目的とはせず、AIエージェントから人間への通知用途に必要な機能を提供する。
- トランスポート層はSTDIOとする。
- 初版の提供バージョンは0.1.0とする。
- `AGENTS.md`に定めるRust、HTTPクライアントのreqwest、非同期制御のtokio、XDG Base Directoryナビゲートのdirectoriesを前提とする。MCP SDKと依存バージョンは設計段階で選定する。

### 1.1 初版の対応範囲

- WindowsとLinuxでの動作を考慮して設計する。両OSの固有挙動に関する仕様は維持するが、CPU別・OS別の実機検証を網羅することは初版の受入条件としない。
- MCPはCodex CLIとClaude Codeでの利用を想定し、両者向けのスキル・設定手順を提供する。実機のMCP接続確認はLinux上のCodex CLIを対象とする。
- 実利用の受入経路は、Linux上のCodex CLIからntfy.shへの送信と、Windows 11のブラウザおよびAndroidのntfyアプリでの受信確認とする。Windows nativeのMCP実行、Claude CodeやiOSアプリの実機確認は必須としない。
- OS・MCPクライアント・ブラウザ・受信アプリのバージョンは実施時に記録し、具体版の事前承認を実装開始の条件としない。最小・最大対応版や全バージョン・全組合せの互換性は保証しない。Rust・SDK・依存バージョンの固定方針は維持する。
- 通知先URLはインスタンスの設定で変更できる。セルフホストの互換APIへの接続を妨げない範囲とするが、セルフホスト全般の動作保証は行わない。
- Markdownとして送信することと、受信アプリによる表示結果は区別する。初版は受信アプリでのMarkdownレンダリングや通知表示の置換を保証しない。

## 2. 機能性要件

### 2.1 通知情報

- 通知としてタイトル、メッセージ本文、優先度、タグ、添付ファイルを扱う。

### 2.2 メッセージ本文

- 本文はMarkdownとして送信する。プレーンテキストとしては送信しない。
- Markdownの元本文は最大1,000文字、かつUTF-8で4,096バイト以下とする。
- 「文字」はUnicodeスカラー値で数え、Markdown記号、空白、改行も含める。結合文字や複数要素の絵文字は複数文字として数え、表示上の文字数とは区別する。
- 上限超過は送信前に入力エラーとして返す。自動切捨て、分割、添付化は行わない。エージェントが要約するか、明示的に添付を指定する。
- 採用する伝送方式で本文を保持できない入力は、添付の有無にかかわらず送信前にエラーとして返す。エージェントが明示的に整形して再送する。具体的な受入判定は設計で定義し、ツールのdescriptionとスキルで明示する。
- 上限と数え方はツールのdescriptionとスキルで周知する。

### 2.3 優先度とタグ

- MCPツールの入力は通知種別に基づき、優先度とタグを以下のとおり決定する。

| 通知の内容 | ntfyのpriority | ntfyのタグ |
|:---|:---|:---|
| バックグラウンド処理の進捗 | `low` | `hourglass_flowing_sand` |
| 通常の完了通知 | `default` | `white_check_mark` |
| ユーザーの判断が必要 | `high` | `question` |
| 障害・セキュリティ・期限切迫 | `urgent` | `rotating_light` |

- 初版は任意タグの追加入力を提供しない。
- 任意の優先度や進捗率に関する情報は本文へ含める。ntfyの優先度を任意指定する入力や、進捗率専用の入力は初版では提供しない。

### 2.5 添付ファイル

- 調査タスクの結果や検索結果などを添付ファイルとして送信できる。
- AIエージェントが作成したコンテンツはntfyサーバへアップロードして添付する。
- エージェントからMCPサーバへの添付入力は、ローカルファイルのパスとデータ直接指定の双方をサポートする。1つの添付にはいずれかの方式を用いる。
- 本文と1つの添付を同じ通知で送信する。受入可能な日本語、内部改行、Markdownのコード例などを含む本文を保持する。
- 採用する伝送方式で本文を保持できない添付同送入力は、送信前にエラーとして返す。前後空白や文字としてのバックスラッシュnなど、伝送時に内容が変わる入力を対象とし、エージェントが明示的に整形して再送する。
- サーバー側の変換を利用した無断の本文変更、自動切捨て、本文だけの送信や別通知への自動変更は行わない。受入制約と具体的な判定条件は設計で定義し、ツールのdescriptionとスキルで明示する。
- 添付の受入上限は2,000,000バイトとし、両入力方式に共通して適用する。直接指定では符号化表現の長さではなく、復元後の実データのサイズで判定する。
- 入力、ファイル読取、上限の問題は送信前に失敗として返す。アップロード失敗は送信失敗として返し、本文だけの通知へ自動変更しない。
- パス指定の元ファイルは変更・削除しない。
- 受入上限は送信成功を保証する値ではない。サーバ側の容量・帯域・認証制限や回線速度によって、上限以下でも送信が失敗し得る。
- 添付のサービス側保持期限や利用枠を、本プロジェクトの固定保証としない。
- データ直接指定の具体的な表現、メタデータ、読取・アップロード方式は設計段階で定義する。

### 2.6 sequence_idによる通知系列の識別

- `sequence_id`は同一タスクに属する通知系列を識別するために使用する。同じIDの通知を同一タスクの進捗・完了として扱い、本文による進捗率の更新などに利用する。
- エージェントは系列IDを指定し、同一タスクの進捗・完了で再利用できる。
- 利用者指定のIDはASCIIの英字・数字・ハイフン・アンダースコアからなる1〜64文字とする。
- ID省略時は、MCPサーバが論理的な1回のツール呼出しにつきIDを生成する。生成・採用したIDをレスポンスに返し、後続通知で再利用できるようにする。送信失敗時も既に生成したIDを返す。
- 自動再試行では系列IDと通知内容を維持する。
- 送信ごとのメッセージIDと系列IDは区別する。系列IDによる通知表示の置換や、履歴の重複排除は保証しない。
- 呼出しをまたぐ永続的なタスク管理は必須としない。IDの生成方式、衝突回避、具体的な入力・出力フィールドは設計段階で定義する。

## 3. 非機能性要件

### 3.1 有料publish機能の不使用

- 電話通知、SMS等、追加料金を発生させ得るpublish機能は使用しない。

### 3.2 認証・HTTPS・情報保護

- topicによる隠蔽、Basic認証、Bearer認証をサポートする。topicによる隠蔽は厳密には認証と異なる。
- HTTPSを必須とする。HTTPへの切替、証明書検証の無効化、認証失敗後の認証なし再送は行わない。
- 認証情報は送信ヘッダーで扱う。
- topic、Basicの資格情報、Bearerトークンをレスポンス、通常ログ、設定表示へそのまま出さず、必要な表示は伏字にする。
- 本文と直接指定データを通常ログへ保存せず、不要な永続保存を避ける。
- 認証情報の保存方法、OS権限などの具体的な管理方法は設計段階で定義する。

### 3.3 設定と通知先

- 設定は以下の方法をサポートし、上から順に評価優先度が高いものとする。

  1. CLIオプション
  2. 環境変数（選別した項目のみ）
  3. 設定ファイル

- 各インスタンスの通知先は、単一のサーバ・topicとして設定で固定する。インスタンスごとの設定変更により、通知先を切り替えられるものとする。
- 設定形式、キー、配置、必須項目、CLI項目、環境変数で扱う項目は設計段階で定義する。

### 3.4 設定不備時の動作

- 起動時に検出できる必須設定不足、不正URL・topic、不完全・矛盾する認証指定、HTTPS以外の指定は、MCP開始前に秘密情報を除いた理由をstderrへ示して異常終了する。
- 明示的に指定された設定ファイルを読めない場合は失敗とし、既定設定へ黙って切り替えない。
- 設定ファイル未指定時の既定ファイル不存在は、他の設定で必須項目がそろっていれば許容する。
- 実行時に判明した認証失敗は、ツールの失敗レスポンスとして返す。

## 4. 送信・再試行・レスポンス要件

### 4.1 タイムアウトと試行回数

- 各HTTP試行の時間上限を5秒とする。添付では、アップロードとレスポンス受領を同じ試行時間に含める。
- 追加再試行は最大3回とし、初回を含む総試行回数は最大4回とする。
- 最初のHTTP送信開始から、再試行の待機を含む全体上限を45秒とする。この上限はローカル添付読取時間を含まない。読取の中断・時間管理は設計段階で具体化する。
- 回線速度によっては、受入上限以下の添付でも試行時間を超えて失敗し得る。

### 4.2 再試行対象と待機

- 一時的な接続・通信エラー、タイムアウト、HTTP 500／502／503／504、一時的な429を再試行対象とする。
- 入力・読取エラー、TLS証明書エラー、認証・権限エラー、サイズ超過、日次枠など直ちに回復しない制限は再試行しない。
- 通常の再試行待機は、順に1秒、2秒、4秒とする。
- 429では、有効な`Retry-After`があれば指定時間より早く再送しない。指定がなければ、待機は順に5秒、10秒、20秒とする。
- 待機と次の試行が全体の時間予算に収まらなければ終了する。待機を短縮して早期再送はしない。このため、最大3回の再試行をすべて実行できない場合がある。
- 再試行対象の厳密な分類表と`Retry-After`の解析・不正値の扱いは、設計段階で定義する。

### 4.3 成否不明とレスポンス

- タイムアウト等によりサーバ側の受領が不明なまま再送すると、通知が重複し得ることを許容する。再試行での系列ID維持は、重複排除の保証を意味しない。
- 後の試行が成功しても、過去試行の受領が不明であれば、レスポンスへ重複可能性を含める。
- レスポンスには、失敗時の分類、秘密情報を除いた説明、取得できたHTTP状態・ntfyエラーコード、試行回数、受領の確認／不明、重複可能性、必要な待機情報、生成・採用済みの系列IDを含める。具体的なフィールドと表現は設計段階で定義する。
- 送信成功はntfyサーバ側の受領確認を意味し、受信端末での表示確認とはしない。

## 5. 利用文書

- AIエージェントへ使用方法を提示するスキル定義と、MCPサーバの設定手順書を提供する。
- スキルには通知の利用場面、通知種別、本文制限と数え方、添付入力、失敗時の扱いを説明する。
- 系列IDを用いた同一タスクへの通知の使用方法と、その通知の契機となる指示をスキル定義で明示する。具体的な指示例と利用方法は後続の利用文書作成で定義する。
- 設定手順書には起動、設定、認証、インスタンス別の通知先切替、確認方法を説明する。
- スキル・手順書の構成、配置、具体的な配布方法は検証・提供構成の合意で確定する。

## 6. 後続で具体化・確認する事項

- 基本設計・CLI仕様・設定仕様で、MCP入出力、送信形式、添付データ表現、ID生成、設定・認証情報管理、OS差異、SDK・依存バージョンを定義する。実機確認の範囲は1.1に従い、環境のバージョンは実施時に記録する。CPU・OS・MCPクライアント・受信アプリの版別マトリクスを必須としない。
- 本体固有の入出力・設定・認証・境界値・エラー・再試行等はローカルまたは模擬環境で検証し、実サービスで全条件を再現することは要求しない。Basic／Bearerの機能仕様は維持するが、実認証アカウントの準備や実サービス認証試験を受入・本ミッション完了の必須条件としない。
- 本文の保持について、添付の有無ごとに受入可能な本文を保持する方式と、保持できない入力を送信前に検出してエラーとする判定条件を設計で定義する。添付同送では符号化後のヘッダーサイズと実際の送信経路での成立を確認する。追加の要求変更が必要なら変更案を提示して再承認を受ける。無断の本文変更・別通知への分離・外部URL指定によってアップロード要件を代用しない。
- 再試行の厳密な分類、レスポンス表現、ローカル添付読取の時間管理をMS1.2で定義する。
- 認証情報確認用のCLIモードとして`--check-auth`を採用する。通知を送らず資格情報の受理だけを確認し、topicの書込権限や通知成功までは確認しない。具体的な動作・出力・終了状態はCLI仕様4章に従う。
- 要件と検証の対応、必要な環境・組合せ・証跡、環境未確保時の扱い、利用文書と本ミッションの開発成果物の構成をMS1.3で合意する。実装・検証・利用文書の本文化は後続Operationで行う。
